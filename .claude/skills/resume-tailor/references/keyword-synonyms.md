# Keyword & Synonym Matching

**Priority note (read first):** Keyword matching is *table-stakes, not the differentiator.* In 2026, semantic ATS matching already bridges most synonyms, and over-optimized keyword-mirrored resumes read as hollow boilerplate to the human who makes the actual decision. So: do this step cleanly and quickly, then stop. The effort that wins interviews goes into the leadership narrative (the micro-story bullets and the skill-stack), not into squeezing in more keywords. Think of this file as "clear the parser and the recruiter's saved search," not "the thing that gets me hired."

The legitimate move: the user did the thing, but called it something other than what the JD calls it. Use the JD's word (or include both forms). This is honest — same work, matched vocabulary. It is NOT license to add a keyword for work the user never did.

## How to use
1. From the target analysis, take the company's terminology list.
2. For each term, check the experience inventory: did the user do this thing under a different name?
3. If yes → rewrite the bullet using the JD's term (or "JD-term (user-term)" if both add value).
4. If no → do not add it. A gap is a gap. Better an honest gap than a lie a recruiter uncovers in five minutes.

## Acronym / full-form pairs — include BOTH forms somewhere in the resume
Different parsers and different recruiter searches index different forms. Spell it out on first use, then the acronym is fine.

## Common equivalent-term families (data leadership)
Pick the JD's variant. These are genuine equivalents, not upgrades:

- **Team leadership:** led / managed / directed / headed / built / grew a team of N. (Match the JD's verb and always keep the real N.)
- **Data pipelines:** data pipelines ≈ ETL/ELT workflows ≈ data ingestion ≈ data integration. (Use what they use.)
- **Analytics function:** analytics ≈ business intelligence ≈ insights ≈ decision science — but these are NOT all identical; only map if the user's actual work fits the JD's meaning.
- **Experimentation:** A/B testing ≈ experimentation ≈ causal inference / online experiments. Only claim causal inference if the user actually did it.
- **Data platform:** data platform ≈ data infrastructure ≈ data architecture ≈ data stack. Map to their framing.
- **Governance:** data governance ≈ data quality ≈ data stewardship ≈ compliance ≈ data trust. Distinct flavors — match precisely.
- **Stakeholder work:** cross-functional collaboration ≈ stakeholder management ≈ business partnering ≈ executive communication.
- **Strategy:** data strategy ≈ roadmap ≈ vision ≈ operating model.
- **Cost:** cost reduction ≈ efficiency ≈ optimization ≈ margin improvement (keep the real number).
- **Cloud/warehouse:** name the specific tech the JD names if the user used it (Snowflake, Databricks, BigQuery, Redshift, dbt, Airflow, Spark, etc.). Specific tool names are high-value exact-match keywords — but only if genuinely used.

## Title mapping
If the user's title doesn't match the target's vocabulary but the scope does, you can add a parenthetical clarifier that reflects reality — e.g., "Analytics Manager (Data Science team lead, 8 reports)". Never invent a title the user didn't hold; clarify scope instead.

## The line you don't cross
Matching vocabulary for real work = good. Adding a skill, tool, or outcome the user didn't have = fabrication. When unsure whether the user's experience genuinely covers a JD term, ask them — don't assume in either direction.
