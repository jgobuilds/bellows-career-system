# ATS-Safe Formatting Rules

These are the mechanical rules that keep a resume parseable across Workday, Greenhouse, Lever, iCIMS, and Taleo. Formatting failures cause roughly a quarter of parsing problems, and they're all preventable. Optimizing for the parser is the same as optimizing for the LLM summary layer on top of it — the AI reads the parsed text, so if the parser drops a section, the AI never sees it either.

## Layout
- **Single column. Always.** Two-column and sidebar layouts are the top failure mode: the parser reads left-to-right across both columns and interleaves your skills into your job titles. Single-column single-handedly avoids the worst bug. (Same-content tests show single-column .docx extracting ~97% of fields vs. ~71% for two-column PDF.)
- **No tables, no text boxes.** Tables look like clean text to you and like merged-cell garbage to the parser. Text boxes get read out of order. Use tab stops or standard word-processor formatting instead.
- **No graphics, logos, charts, photos, skill-rating bars, or icons.** The parser can't read an image; a skills bar chart contributes zero matchable keywords.
- **Nothing critical in the header/footer.** Many parsers don't read the header/footer region. Name, email, phone, LinkedIn go in the body of page one as normal text.

## Sections
- **Standard headers only:** "Experience" (or "Work Experience"), "Education," "Skills," "Certifications," "Summary." Creative headers like "Where I've Made an Impact" or "My Journey" break the field mapping — the parser doesn't recognize the section and may ignore everything in it.
- **Skills section is now load-bearing.** 2026 screening is increasingly skills-based: many enterprise teams filter by required skills before reading job history. On Greenhouse and Workday the Skills block is among the first things mapped to scorecard criteria. Include a real, honest skills block with the JD's terminology.
- **Recommended order for leadership roles:** Contact → Leadership Snapshot (3-5 lines) → Core Competencies (keyword block) → Experience → Education → Certifications. Recency matters: parsers weight content near the top higher, so the most relevant, most quantified material goes up top.

## Core competencies block
- **Keep each competency short — a 2-4 word scannable phrase.** No long tool parentheticals inside a competency (not "AI & Automation Enablement (Cursor, GitHub Copilot, Atlassian Rovo, MCP, core agents)"; just "AI & Automation Enablement").
- **Put specific tools/platforms in a separate compact "Technical Skills" line**, grouped (cloud/warehouse; AI tooling; BI; transformation). The competencies stay scannable for the human; the tools stay keyword-matchable for the ATS.

## Work authorization / citizenship
- **Keep it implicit by default.** Do not add a standalone "U.S. Citizen" / work-authorization line to the header or summary — a long, continuous domestic work history conveys it. An explicit line reads as filler and dates the document.
- State it explicitly **only** when a posting makes it a hard knockout (active clearance or ITAR/defense role that screens on it), and confirm with the user first. Raise it in the cover letter or interview, not the resume banner.

## Dates
- **One consistent format:** `Month YYYY` (March 2024) or `MM/YYYY` (03/2024) throughout. Parsers compute tenure and flag gaps from dates; mixed formats produce misread employment periods and can rank you below people whose dates parsed cleanly.
- Avoid "current"/"ongoing" alone — use `March 2024 – Present`.

## Fonts & file
- **Standard fonts:** Arial, Calibri, Helvetica, Georgia, Times New Roman, Roboto. No custom/downloaded fonts.
- **File format:** `.docx` is the most universally parsed and the safest default. PDF preserves formatting but only use a **text-selectable** PDF (never a scanned/image PDF). If the application form asks for Word, give Word.
- **Test:** you should be able to select and copy all text. If you can't select it, the parser can't read it.

## File naming & metadata (honest, not disguised)
- **Human filenames.** `Firstname Lastname - Resume.docx` / `Firstname Lastname - Cover Letter.docx`. Put the company/role in the folder, not a role-encoded filename slug — long per-role slugs read as rote batch output.
- **Normalize metadata honestly.** Programmatic .docx generation misattributes the file (creator = the library name, a "generated by ..." description, a stale template timestamp). Correct it: author/last-modified-by = the candidate (they wrote the content; the tool only rendered it), blank the description and Company, created/modified = the real generation time, revision = 1 (first save), Application blank. It CORRECTS the misattribution and drops the generator advert — it does NOT backdate the file, inflate the revision, or claim it was made in Word. Metadata only, never content. (docx_finalize.py does exactly this.)

## Output files (docx + pdf, and where they live)
- **Deliver both a `.docx` and a text-selectable `.pdf`** for every resume and cover letter (render the .docx to PDF; never a scanned/image PDF). The .docx stays the safest for ATS parsing; the PDF is for human-facing sends (email, referrer) and applications that ask for PDF.
- **Tailored** resumes/cover letters live in `personal/applications/<company>/`. The **generic / master** resume lives at the **root of the `personal/applications/` folder** (`personal/applications/Firstname Lastname - Resume.docx`), not the repo root.

## Name (legal + preferred)
- Header shows the legal first name plus the preferred name in parentheses when they differ (e.g. **"LEGALFIRST (PREFERRED) LASTNAME, M.S."**), so background checks match the legal name while recruiters see the name the candidate actually uses. Metadata author = the legal name. (If legal and preferred are the same, just use it plainly.)

## Length
- **Target two full pages** for senior/executive resumes (the one-page rule is dead at leadership level). Fill the second page; do not leave it a sparse stub, and do not spill onto a third.
- **Selection is the lever, not font size.** The profile holds more achievements than fit: select the most role-relevant first, then add the next-most-relevant until page two is full. If it overflows, cut the least-relevant bullets or tighten wording. Never shrink fonts/margins or pad with filler.
- Prioritize by relevance to the role thesis, then quantified impact, then recency. **Verify by rendering to PDF** and adjust the selection to land on two full pages.

## What NEVER to do
- No white/invisible text, no keyword stuffing in tiny or background-colored fonts, no hidden layers, no metadata keyword tricks. These are detected as manipulative in 2026 and flag the application. They also insult the intelligence of the human who reads the resume two steps later. The honest keyword match (real work, matched vocabulary) is both safe and more effective.
